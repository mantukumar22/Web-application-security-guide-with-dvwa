# 09 — Weak Session IDs

## What the feature does
A "generate session ID" button, illustrating how session/token generation schemes vary in unpredictability.

---

## LOW

```php
$cookie_value = $last_session_id + 1;   // simple sequential increment
setcookie( "dvwaSession", $cookie_value );
```

**Exploitation:** If session IDs are **sequential integers**, an attacker who obtains any one valid session ID (their own, or one leaked via logs/Referer/XSS) can simply **increment or decrement** it to guess other users' active session IDs and hijack their sessions.

```bash
for i in $(seq 1000 1100); do
  curl -s -H "Cookie: dvwaSession=$i" http://127.0.0.1:42001/dvwa/vulnerabilities/weak_id/ ;
done
```

**Why it works:** Sequential/predictable identifiers used as authentication tokens fail the core requirement of a session ID: **unguessability**. Knowing one value lets you predict adjacent valid values.

---

## MEDIUM

```php
$cookie_value = md5( time() );  // hash of the current server timestamp
```

**Why it's still bypassable:** Hashing doesn't add entropy if the *input* has low entropy. `time()` returns Unix time in **seconds** — an attacker who knows roughly when a victim's session was created (e.g. from an HTTP `Date` response header, or just by trying values within a plausible few-second/minute window around a known event) can **brute-force the small search space** of candidate timestamps, hash each one, and find matches:

```python
import hashlib, requests

for t in range(known_time - 300, known_time + 300):
    candidate = hashlib.md5(str(t).encode()).hexdigest()
    r = requests.get(url, cookies={"dvwaSession": candidate})
    # check response for "logged in" indicator
```

**Root issue:** `md5(predictable_input)` is still predictable — hashing is not a substitute for a cryptographically secure random source; entropy must come from the *input*, not the hash function.

---

## HIGH

```php
$cookie_value = md5( uniqid() );   // uniqid() adds microsecond precision + optional entropy
```

**Why it's still (somewhat) bypassable:** `uniqid()` without the `more_entropy` flag is based on the current time in **microseconds** — far higher resolution than `time()`, making brute force much harder but not information-theoretically impossible against a narrowly-known time window and enough compute; PHP's own docs note `uniqid()` alone is **not suitable for security purposes** because it's still fundamentally time-derived, not a CSPRNG. It raises the brute-force cost from "trivial" to "impractical for most attackers," but it's the wrong primitive on principle.

**Root issue:** Still deriving "randomness" from a timestamp-based function rather than a cryptographically secure random number generator (CSPRNG).

---

## IMPOSSIBLE

```php
$cookie_value = sha1( mt_rand() . microtime() . uniqid() . mt_rand() );
// Real production code should use:
$cookie_value = bin2hex(random_bytes(32));  // PHP's CSPRNG, 256 bits of entropy
```

**Why this is actually secure:** True session tokens must be generated from a **cryptographically secure random number generator** with sufficient entropy (128+ bits) that brute-forcing the space is computationally infeasible (more attempts than atoms in the observable universe, at real-world rate limits). Unlike time-derived values, a CSPRNG output has no external correlation an attacker can use to narrow the search space — knowing the exact server time, or even every other issued session ID, gives zero information about the next one.

---

## Root Cause Summary
> Session/token identifiers must be generated by a cryptographically secure random number generator with sufficient entropy — never derived from sequential counters or timestamps, even when hashed. Hashing a predictable input produces a predictable (just longer-looking) output.

## Real-World Parallels
- Historic vulnerabilities in early web frameworks using `rand()`/timestamp-seeded session IDs
- CVE-class: "predictable password reset token" bugs (same root cause, different token purpose) — a frequent bug bounty submission category
- OWASP Top 10: **A02:2021 – Cryptographic Failures**

## Mitigation Checklist
- [ ] Use the platform's CSPRNG (`random_bytes()` in PHP, `secrets` module in Python, `crypto.randomBytes()` in Node)
- [ ] Minimum 128 bits of entropy for session tokens
- [ ] Never derive tokens from time, sequence, or other predictable/observable values
- [ ] Rotate session IDs on privilege change (e.g. login) to prevent fixation
- [ ] Set `HttpOnly`, `Secure`, and `SameSite` flags on session cookies
